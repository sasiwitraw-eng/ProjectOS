# Producer-Consumer Multi-Threaded Engine

โปรแกรมจำลองการทำงานของอัลกอริทึม **Producer-Consumer Problem (Bounded-Buffer Problem)** แบบ Multi-threaded ในรายวิชาระบบปฏิบัติการ (Operating Systems) พัฒนาด้วยภาษา C ร่วมกับไลบรารี **POSIX Threads (`pthread`)** และแสดงผลการทำงานแบบ Real-time Interactive Dashboard ด้วย **Raylib GUI**

---

## 1. การเริ่มต้นใช้งานและเลือกโหมด (Getting Started)

เมื่อสั่งรันโปรแกรม (`./app`) หน้าจอแรกจะเป็น **หน้าเลือกกลไกการจัดการ Synchronization (Mode Selection Screen)** ซึ่งผู้ใช้สามารถคลิกเลือกได้ 2 รูปแบบ:

1. **ปุ่มสีฟ้า `POSIX Semaphore + Mutex`**
   * ใช้ **Counting Semaphore** 2 ตัว ได้แก่ `sem_empty` (นับจำนวนช่องว่างในคิว) และ `sem_full` (นับจำนวนสินค้าที่มีในคิว) ร่วมกับ **Mutex Lock** (`buffer_mutex`)
   * เมื่อคิวเต็ม `sem_empty` จะมีค่าเป็น 0 ทำให้ Producer ที่เรียก `sem_wait()` ถูกบล็อก (Sleep/Wait) อัตโนมัติ และเมื่อคิวว่าง `sem_full` จะมีค่าเป็น 0 ทำให้ Consumer ถูกบล็อกเช่นกัน
2. **ปุ่มสีส้ม `Mutex + Condition Variable`**
   * ใช้ **Mutex Lock** ร่วมกับตัวแปรเงื่อนไข `cond_empty` และ `cond_full`
   * เมื่อคิวเต็ม Producer จะเรียก `pthread_cond_wait()` เพื่อหยุดรอและคลายล็อก Mutex ชั่วคราว จนกว่า Consumer จะดึงข้อมูลออกแล้วส่งสัญญาณ `pthread_cond_signal()` มาปลุก

*(หมายเหตุ: สามารถข้ามหน้าเลือกโหมดด้วยการรันผ่านคำสั่ง `./app sem` หรือ `./app cond` จาก Terminal ได้โดยตรง)*

## 2. รายละเอียดส่วนประกอบบนหน้าจอ (Dashboard Breakdown)

หน้าจอหลักคือแดชบอร์ดจำลองการทำงานของอัลกอริทึม **Producer-Consumer Problem** แบบ Multi-threaded โดยมีรายละเอียดแบ่งตามส่วนประกอบ 4 ส่วนหลักดังนี้:

### 2.1 Header & Operation Mode (แถบด้านบน)
* **Title:** `Producer-Consumer Multi-Threaded Engine`
* **Mode Indicator (มุมขวาบน):** แสดงโหมด Synchronization ที่กำลังทำงานอยู่ในรอบนั้น เช่น:
  * `Mode: POSIX Semaphore` (ป้ายสีฟ้า) — ระบบใช้ **Semaphore** (`sem_empty`, `sem_full`) ร่วมกับ **Mutex Lock**
  * `Mode: Mutex + CondVar` (ป้ายสีส้ม) — ระบบใช้ **Condition Variable** ร่วมกับ **Mutex Lock**
  * **หน้าที่หลัก:** ป้องกันปัญหา **Data Race (Race Condition)** เมื่อมีหลาย Thread เข้าถึง Buffer พร้อมกัน และป้องกันการเขียนข้อมูลทับซ้อน

---

### 2.2 Bounded Buffer Queue (แผงแสดงสถานะ Buffer ตรงกลางซ้าย)
แสดงคิวเก็บข้อมูลที่มีโครงสร้างแบบ **Circular Buffer (Ring Buffer / เข้าก่อน-ออกก่อน FIFO)**
* **ขนาดความจุเริ่มต้น:** 10 ช่อง (`Slot 0` ถึง `Slot 9`) โดยสามารถปรับลด-เพิ่มได้ตั้งแต่ 5 ถึง 20 ช่อง
* **หลักการทำงานของคิววงกลม:**
  * ตัวชี้ฝั่งผลิต (`in_idx`) จะวางชิ้นงานเรียงจาก Slot 0 ไปจนถึงช่องสุดท้าย แล้ววนกลับมาที่ Slot 0 ใหม่
  * ตัวชี้ฝั่งบริโภค (`out_idx`) จะดึงชิ้นงานเก่าที่สุดออกไปตามลำดับ
* **การอ่านสถานะจากหน้าจอ (ตัวอย่างขณะทำงาน):**
  * มีข้อมูลตกค้างอยู่ในคิว **6 ชิ้น** (`Slot 4` ถึง `Slot 9`) ส่วน `Slot 0` – `Slot 3` ว่างอยู่ (เนื่องจากถูก Consumer ดึงออกไปประมวลผลแล้ว)
* **สีและหมายเลข ID ของชิ้นงาน:**
  * หมายเลข `#ID` จะถูกออกภายใน **Critical Section** (ภายใต้ Mutex Lock) ทำให้เลขเรียงลำดับตามการเข้าคิวจริงเสมอ ไม่มีเลขซ้ำหรือข้ามลำดับ
  * สีของกล่องชิ้นงานระบุว่าผลิตโดย Thread ตัวใด เช่น:
    * **ชิ้นงาน #15, #17, #20 (สีแดง):** ผลิตโดย Thread **P0**
    * **ชิ้นงาน #16, #18, #19 (สีส้ม):** ผลิตโดย Thread **P1**

---

### 2.3 Control Panel (แผงควบคุมพารามิเตอร์ ตรงกลางขวา)
แผงควบคุมแบบ Interactive ที่ให้ผู้ใช้กดปุ่ม **`-`** และ **`+`** เพื่อปรับพารามิเตอร์ของระบบได้แบบ Real-time ขณะที่ Thread กำลังวิ่งอยู่ (ใช้ตัวแปรแบบ `_Atomic` และ `Mutex` เพื่อความปลอดภัยของข้อมูล):

* **Producers (N): 2** — จำนวน Thread ฝั่งผู้ผลิตที่กำลังทำงานอยู่ (ปรับได้ 1 ถึง 10 Threads)
* **Consumers (M): 2** — จำนวน Thread ฝั่งผู้บริโภคที่กำลังทำงานอยู่ (ปรับได้ 1 ถึง 10 Threads)
* **Capacity: 10** — ขนาดความจุสูงสุดของ Buffer (ปรับได้ 5 ถึง 20 ช่อง)
* **Prod Delay: 0.8s** — เวลาหน่วงที่ Producerแต่ละตัวใช้ในการผลิตสินค้า 1 ชิ้น (ปรับได้ 0.2s ถึง 3.0s)
* **Cons Delay: 1.2s** — เวลาหน่วงที่ Consumer แต่ละตัวใช้ในการดึงสินค้าไปใช้ 1 ชิ้น (ปรับได้ 0.2s ถึง 3.0s)
* **Active Producer Threads:** แถบสัญลักษณ์แสดงสีประจำตัวของ Thread ผู้ผลิตที่เปิดใช้งานอยู่ทั้งหมด (เช่น `P0` = สีแดง, `P1` = สีส้ม, `P2` = สีทอง ฯลฯ)

> **การวิเคราะห์สภาวะระบบจากค่าพารามิเตอร์:**
> ในสภาวะที่ฝั่ง Producer มีความเร็วในการผลิตสูงกว่า (`Prod Delay 0.8s`) ฝั่ง Consumer ที่ดึงไปใช้งาน (`Cons Delay 1.2s`) โดยมีจำนวน Thread เท่ากัน (N=2, M=2) จะส่งผลให้สินค้าถูกผลิตเข้ามาเร็วกว่าการระบายออก สินค้าจึงเริ่มสะสมในคิวเพิ่มขึ้นเรื่อยๆ (เช่น ขึ้นมาที่ 60%) จนกระทั่งเต็ม 100%

### 2.4 Real-Time Analytics & System Status (แผงสถิติตัวเลขด้านล่าง)
แสดงตัวชี้วัดประสิทธิภาพและสถานะทางระบบปฏิบัติการแบบวินาทีต่อวินาที:

1. **THROUGHPUT (`2.0 items / sec`):**
   * วัดความเร็วในการประมวลผลสำเร็จของระบบ (จำนวนชิ้นงานที่ Consumer ดึงออกจากคิวได้จริงในรอบ 1 วินาทีที่ผ่านมา)
2. **UTILIZATION (`60.0%`):**
   * อัตราการใช้งานพื้นที่ Buffer ณ ปัจจุบัน คำนวณจาก `(จำนวนของในคิว / ขนาด Capacity) × 100`
   * แสดงผลพร้อม Progress Bar สีทอง และตัวเลขจำนวนช่อง เช่น `6 / 10 slots`
3. **THREAD BLOCKS (ตัวนับจำนวนครั้งที่ Thread ถูกสั่งให้หยุดรอ):**
   * **`Prod: 0` (สีแดง):** จำนวนครั้งที่ Thread ผู้ผลิตพยายามจะวางชิ้นงาน แต่ **Buffer เต็ม 100%** จึงถูกระบบ Synchronization สั่งให้หยุดรอ (Blocked)
   * **`Cons: 0` (สีส้ม):** จำนวนครั้งที่ Thread ผู้บริโภคพยายามจะดึงชิ้นงาน แต่ **Buffer ว่างเปล่า (0%)** จึงถูกสั่งให้หยุดรอจนกว่าจะมีสินค้าใหม่เข้ามา
4. **TOTAL PROCESSED (ยอดสะสมรวมตั้งแต่เริ่มรัน):**
   * **`Produced: 20`:** ยอดรวมสินค้าที่ถูกผลิตเข้าสู่ระบบทั้งหมด = 20 ชิ้น
   * **`Consumed: 14`:** ยอดรวมสินค้าที่ถูกดึงออกไปใช้ทั้งหมด = 14 ชิ้น
   * **การตรวจสอบความถูกต้อง (Data Integrity Check):**
     $$\text{จำนวนคงเหลือในคิว} = \text{Produced} - \text{Consumed}$$
     จากตัวอย่าง `20 - 14 = 6 ชิ้น` ซึ่งตรงกับจำนวนกล่องในคิว (Slot 4 ถึง Slot 9) พอดี เป็นการพิสูจน์ว่าไม่มีข้อมูลสูญหาย (Lost Update) หรือการอ่านเขียนทับซ้อน (Race Condition)

## 3. คู่มือการใช้งานปุ่มควบคุม (Interactive Control Guide)

ผู้ใช้สามารถทดลองกดปุ่มในกรอบ **Control Panel** เพื่อดูการเปลี่ยนแปลงของระบบได้ทันที ดังนี้:

| ปุ่มควบคุม | การกดปุ่ม `+` | การกดปุ่ม `-` | ผลกระทบต่อระบบ (OS Behavior) |
| :--- | :--- | :--- | :--- |
| **Producers (N)** | เพิ่มจำนวน Thread ผู้ผลิต (สูงสุด 10) | ลดจำนวน Thread ผู้ผลิต (ต่ำสุด 1) | ยิ่ง N มาก อัตราการเติมของเข้า Buffer ยิ่งเร็วขึ้น และมีสีของชิ้นงานหลากหลายขึ้นตามรหัส `P0–P9` |
| **Consumers (M)** | เพิ่มจำนวน Thread ผู้บริโภค (สูงสุด 10) | ลดจำนวน Thread ผู้บริโภค (ต่ำสุด 1) | ยิ่ง M มาก อัตราการดึงของออกจาก Buffer ยิ่งเร็วขึ้น ค่า Throughput จะสูงขึ้น |
| **Capacity** | ขยายขนาดช่องเก็บของทีละ 1 ช่อง (สูงสุด 20) | ลดขนาดช่องเก็บของทีละ 1 ช่อง (ต่ำสุด 5) | ระบบจะจัดเรียงข้อมูลใน Ring Buffer ใหม่โดยอัตโนมัติ หากกด `+` ตอนคิวเต็ม จะไปปลุก Producer ที่ติด Block ให้ทำงานต่อทันที **แต่หากกด `-` ตอนที่มีของในคิวมากกว่าขนาดใหม่ ระบบจะปฏิเสธและแจ้งเตือน `"Buffer too full to shrink"` เพื่อป้องกันข้อมูลสูญหาย** |
| **Prod Delay** | เพิ่มเวลาผลิตทีละ 0.2s (ผลิตช้าลง) | ลดเวลาผลิตทีละ 0.2s (ผลิตเร็วขึ้น) | ใช้ปรับความเร็วในการสร้างชิ้นงานของแต่ละ Producer Thread |
| **Cons Delay** | เพิ่มเวลาบริโภคทีละ 0.2s (ดึงช้าลง) | ลดเวลาบริโภคทีละ 0.2s (ดึงเร็วขึ้น) | ใช้ปรับความเร็วในการดึงชิ้นงานไปใช้ของแต่ละ Consumer Thread |

## 4. การจำลองสถานการณ์สำคัญทาง OS (Simulation Scenarios)

ในการทดสอบหรือสาธิตการทำงานของโปรแกรม สามารถทดลองปรับค่าตาม 3 สถานการณ์หลักดังนี้:

### สถานการณ์ที่ 1: ทดสอบสภาวะคิวเต็ม (Buffer Full / Producer Blocking)
1. กดเพิ่ม **`Producers (N)`** เป็น `5` และลด **`Prod Delay`** ลงเหลือ `0.4s`
2. ปล่อยให้ **`Consumers (M)`** อยู่ที่ `2` และ **`Cons Delay`** อยู่ที่ `1.2s`
3. **ผลลัพธ์ที่สังเกตได้:**
   * ช่อง Buffer ทั้ง 10 ช่องจะถูกเติมจนเต็มอย่างรวดเร็ว (`UTILIZATION = 100.0%`)
   * เมื่อเต็มแล้ว Producer จะไม่สามารถเขียนข้อมูลทับช่องเดิมได้ และจะถูกสั่งให้หยุดรอ
   * ตัวเลข **`THREAD BLOCKS -> Prod`** จะเพิ่มขึ้นเรื่อยๆ ตามจำนวนครั้งที่ Producer พยายามเข้าคิวตอนเต็ม

### สถานการณ์ที่ 2: ทดสอบสภาวะคิวว่าง (Buffer Empty / Consumer Blocking)
1. กดลด **`Producers (N)`** เหลือ `1` และเพิ่ม **`Prod Delay`** เป็น `1.4s`
2. กดเพิ่ม **`Consumers (M)`** เป็น `6` และลด **`Cons Delay`** เหลือ `0.2s`
3. **ผลลัพธ์ที่สังเกตได้:**
   * ชิ้นงานในคิวจะถูกดึงออกไปใช้จนหมดเกลี้ยง (`UTILIZATION = 0.0%`)
   * Consumer ที่พยายามดึงข้อมูลจากคิวว่างจะถูกสั่งให้หยุดรอทันที
   * ตัวเลข **`THREAD BLOCKS -> Cons`** จะเพิ่มขึ้นเรื่อยๆ จนกว่า Producer จะผลิตชิ้นงานใหม่เข้ามาส่ง

### สถานการณ์ที่ 3: ทดสอบการขยายและลดขนาดคิวแบบ Dynamic (Dynamic Resizing)
1. ทำให้คิวเต็ม 10 ช่อง (ตามสถานการณ์ที่ 1)
2. ลองกดปุ่ม **`-`** ที่ **Capacity** จะพบข้อความแจ้งเตือนสีแดง **`Buffer too full to shrink`** เพราะมีของอยู่เต็ม 10 ชิ้น ไม่สามารถหดคิวเหลือ 9 ช่องได้
3. ลองกดปุ่ม **`+`** ที่ **Capacity** เพิ่มเป็น `15` ช่อง จะเห็นช่อง `Slot 10` – `Slot 14` เพิ่มขึ้นมาบนหน้าจอทันที และ Producer ที่ติดบล็อกอยู่จะถูกปลุกขึ้นมาใส่ข้อมูลต่อได้ทันที

## 5. วิธีติดตั้งและรันโปรแกรม (How to Build & Run)

โค้ดถูกออกแบบให้รองรับการทำงานข้ามแพลตฟอร์ม (Cross-platform) ทั้งบน **Ubuntu / Linux (WSL)**, **macOS**, และ **Windows**

### 5.1 บน Ubuntu / Linux หรือ Windows Subsystem for Linux (WSL)
```bash
# 1. ติดตั้งคอมไพเลอร์และไลบรารี Raylib (ทำครั้งแรกครั้งเดียว)
sudo apt update
sudo apt install -y build-essential libraylib-dev libgl1-mesa-dev libx11-dev

# 2. คอมไพล์และรันโปรแกรม
gcc main.c -o app -lraylib -lGL -lm -lpthread -ldl -lrt -lX11
./app
```

### 5.2 บน macOS (Apple Silicon / Homebrew)
```bash
# 1. ติดตั้ง Raylib ผ่าน Homebrew
brew install raylib

# 2. คอมไพล์และรันโปรแกรม
gcc main.c -o app -I/opt/homebrew/include -L/opt/homebrew/lib -lraylib -lpthread -lm
./app
```

### 5.3 บน Windows (ผ่าน MSYS2 / MinGW64)
```bash
gcc main.c -o app.exe -lraylib -lopengl32 -lgdi32 -lwinmm -lpthread
./app.exe
```

### การปิดโปรแกรมและการคืนทรัพยากร (Graceful Shutdown)
เมื่อผู้ใช้กดปุ่มกากบาทปิดหน้าต่าง หรือกดปุ่ม `ESC`:
1. ระบบจะเปลี่ยนสถานะตัวแปร `running` เป็น `false`
2. ส่งสัญญาณ `sem_post()` และ `pthread_cond_broadcast()` เพื่อปลุกทุก Thread ที่อาจค้างอยู่ในสถานะรอ (Blocked)
3. เรียกใช้ `pthread_join()` เพื่อรอให้ Producer และ Consumer ทุกตัวจบการทำงานอย่างสมบูรณ์
4. ทำลาย Mutex, Condition Variable และ Semaphore (`sem_destroy` / `sem_unlink`) เพื่อคืนทรัพยากรให้ระบบปฏิบัติการอย่างปลอดภัยโดยไม่เกิด Memory Leak
